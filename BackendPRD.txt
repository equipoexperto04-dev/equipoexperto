BACKEND PRD — Self-Serve Recipes SaaS (n8n-powered)
1) Goal

Build a backend for a multi-tenant SaaS that allows non-technical SMB users to activate “Recipes” with a toggle, while the execution is handled by n8n workflows.

The backend must provide:

Auth + organization (multi-tenant)

Recipe catalog + per-user enablement

Secure webhook endpoints for n8n triggers

Config storage (per recipe per tenant)

Execution logs + status

Review funnel redirect logic (positive → Google review; negative → private feedback)

Admin operations

Future-ready billing hooks (Stripe-ready but not required in MVP)

2) Key Concepts
Tenant / Workspace

A workspace represents a company (e.g., Equipo Experto client). Each user belongs to a workspace.

Recipe

A “Recipe” is a productized automation template (implemented in n8n).
Example recipes:

Review funnel

Lead capture auto-response

Lead follow-up sequence

Installation (Enabled Recipe)

A workspace can “install” a recipe → saved config + status ON/OFF.

Event

Any inbound lead/survey/trigger that enters the system, gets stored and can be forwarded to n8n.

3) Recommended Tech Stack

API: Node.js (NestJS/Express) or Laravel

DB: PostgreSQL

Cache/Queue (optional MVP): Redis (for rate limits / future jobs)

Auth: JWT + refresh tokens

Hosting: VPS + Docker

File storage (optional): S3-compatible for assets

Observability: basic server logs + DB logs

When user enables a recipe, backend creates an installation record.

E) Secure Webhooks & n8n Integration Layer

This is the heart of the backend.

1) Incoming webhooks (from websites/forms/ads/qr/sms links)

Backend provides endpoints like:

POST /hooks/:workspaceSlug/:recipeSlug/:source

POST /hooks/:installationId

Security

Either:

signed secret in header X-Recipe-Signature

or token in header Authorization: Bearer <token>

Rate limit per workspace + IP

Validate payload shape & size (prevent abuse)

Store request payload in DB as an Event

2) Outgoing delivery to n8n

Two patterns (choose one for MVP):

Pattern A (recommended): n8n pulls

Backend stores events

n8n periodically pulls via API: GET /events?status=pending

n8n marks processed: POST /events/:id/ack

Pros: reliable, retries controlled.
Cons: requires polling.

Pattern B: backend pushes to n8n

Backend immediately forwards event to a workspace’s configured n8n webhook endpoint

Pros: real-time, simpler UI.
Cons: retries, outages more complex.

✅ For MVP: Pattern B is acceptable if you implement retries (3 attempts) and logging.

3) n8n callback for results/logging

n8n should call:

POST /n8n/callback
Payload includes:

installationId

eventId

status (success/failed)

message

external ids (email provider message id, whatsapp id, etc.)

Backend stores it in logs.

F) Review Funnel Redirect System (Critical)

This is NOT n8n-dependent — it’s a product UX feature.

Flow

Customer opens a survey link generated by backend

Survey submitted → backend calculates score

Backend redirects:

positive → Google Review URL

negative → private feedback page or thank-you page, plus notify workflow (n8n)

Endpoints

GET /r/:token → opens branded survey page (frontend) OR returns survey config (if frontend handled separately)

POST /r/:token/submit → stores response + redirects

Logic rules

threshold configurable per installation (default 4/5)

googleReviewUrl stored per installation

privateFeedbackDestination can be:

internal “thank you” page

or workspace website URL

Data to store

rating

optional comment

customer contact (optional)

timestamp

outcome: redirect_google or private_feedback

7) Non-Functional Requirements
Reliability

Webhook ingestion must be fast (<500ms average)

Store first, process second (never lose events)

Retry forwarding to n8n up to 3 times

Security

HTTPS only

token hashing at rest

input validation + payload size limits

per-workspace rate limiting

audit trail logs

Compliance (basic)

ability to delete workspace data on request (manual admin command in MVP)
